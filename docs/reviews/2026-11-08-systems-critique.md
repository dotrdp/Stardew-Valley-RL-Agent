# Rust-systems critique of DESIGN.md v1/v2 (2026-11-08)

Produced by an independent review agent; amendments are folded into DESIGN.md v2.1.

## Summary

The design is sound in outline: in-crate RNG, same-step auto-reset into preallocated buffers, stepping with the GIL released, f16 observations and bit-packed masks. Eight contract-level defects should be fixed before code exists, all MUST below.

1. **`.npz` shards can't be memory-mapped.** numpy silently ignores `mmap_mode` for `.npz`. Reading one row of a 64 MiB array took 28 ms (stored) or 185 ms (deflated), versus 0.38 ms from a `.npy`. That breaks §6's "memory-mapped shards".
2. **The new §3.7 VecEnv copies outputs while holding the GIL.** Its "fresh arrays copied out after the GIL is re-acquired" costs about 548 µs per call at N=1024. A 1024-env call only has 512 µs at the 2M primitive-steps/s target. Allocating fresh arrays and filling them in place costs about 1 µs extra.
3. **Final observation and reset seeds are underspecified.** Only `final_global` is kept, but Gymnasium 1.4's SAME_STEP mode needs the full observation in `infos['final_obs']`. The seed used for each auto-reset is not defined.
4. **Episodes can be infinite.** Tick costs for actions 7–54 are unspecified. A zero-tick action lets a policy stall forever: `max_days` never fires and the per-day penalty is never charged.
5. **`pub const OBS_GLOBAL_DIM` contradicts runtime TOML parsing.** Separately, ids taken from table order are unstable: the `toml` crate's map is alphabetical by default and insertion-ordered if any crate enables `preserve_order`.
6. **There is no SIM_VERSION and no stable state hash.** The std docs say `DefaultHasher` must not be relied on across releases, and `f32::ln` precision varies by platform.
7. **The dataset can't hold DAgger data.** It has no expert-label column, and `done` does not separate terminated from truncated.
8. **`furrow-py`'s `[lib] name = "furrow"` collides with the `furrow` crate.** Cargo warns about `target/debug/libfurrow.rlib` and says the collision "may become a hard error".

**What I tested:**
- **Bindings.** I built the zero-copy + `py.detach` pattern against pyo3 0.30.1 / numpy 0.30.0, also as an abi3-py311 build, and ran it with the venv's Python 3.13.
  - The GIL is released.
  - A second concurrent caller gets `RuntimeError: Already borrowed`.
  - Strided output arrays are rejected; `rollout[t]` slices are written in place.
  - Fixed overhead is about 5–15 µs per call.
  - int32 actions raise `TypeError`, so the binding needs `AllowTypeChange`.
- **Load imbalance.** I measured rayon on this Ryzen 7 9700X, which has 8 cores / 16 threads, not the "16-core desktop" in the targets. With heavy-tailed macro costs, lockstep efficiency was 11/23/46/75% at N=16/64/256/1024. Stragglers cause this, not rayon. The fixes are per-macro time budgets, running non-neural workloads episode by episode in parallel, and `with_max_len(1)`.

**SHOULD items:** scheduling, libm/HashMap lints with an allocation-free test, action logs as the source of truth, SoA arena memory layout, pathfinding, keyed RNG streams, test suites, CI pinning plus a macOS determinism job, benchmark methodology, crate boundaries.

## Amendments

### 1. [must] §5 Trajectory format — shard container

**Change.** Replace the `shard_00000.npz, … (~2^20 steps each)` bullet with: `shards/<writer>-<seq>/` holds one raw .npy per array (`obs_global.npy`, `obs_grid.npy`, `action.npy`, …): little-endian, C-order, uncompressed, npy v1.0 header padded so data starts 64-byte aligned. (1) Shards are cut only at episode boundaries and sized by bytes: target ≤ 512 MiB, with bytes/step ≈ 2·G + C·(2r+1)² + ⌈A/8⌉ + ~24. (2) Writers stream rows into `shards/.tmp-<id>/`, patch each header's shape on close, fsync, rename atomically, and only then append that shard's lines to episodes.jsonl, so a crash leaves only an ignored temp dir. (3) Concurrent writers use distinct `<writer>` prefixes. (4) zstd of whole shard dirs is for archival/transfer only. (5) Readers: `np.load(f, mmap_mode='r')` in svrl.data and memmap2 in furrow_traj::Reader. (6) Drop `zip` from [workspace.dependencies].

**Rationale.** §6 promises memory-mapped shards, but numpy silently ignores mmap_mode for .npz. Measured with the venv's numpy 2.5.4 on a 64 MiB f16 array: one row took 28 ms from a stored .npz and 185 ms from a deflated one, because the whole member is read or decompressed. The same row took 0.38 ms from a .npy, which loads as np.memmap with data at a 64-aligned offset. With ~3–4 GB shards (2^20 steps × ~3–4 KB), uniform step sampling would read gigabytes per minibatch. npz also can't be appended in place, and single-threaded deflate would bottleneck the 20k macro-steps/s generator.

### 2. [must] §3.2 VecEnv auto-reset semantics (and the §3.7 info dict)

**Change.** Replace the VecEnv paragraph with a normative spec. (1) API: `VecEnv::new(cfg, num_envs, num_threads)`; `reset(&mut self, out: &mut VecOut)`; `step(&mut self, actions: &[u32], out: &mut VecOut) -> Result<(), StepError>` (Err on wrong length or action ≥ num_actions); `envs()` and `envs_mut()`. (2) VecOut holds caller-owned slices: obs_global [N·G] f32, obs_grid Option<[N·C·H·W] u8>, mask [N·A] bool; reward f32, terminated bool, truncated bool, ticks u32 (each [N]); final_global, final_grid, final_mask; ep_return f32, ep_days u16, ep_ticks u32, ep_success bool, ep_seed u64, ep_slots/requests/wings u16 (each [N]). (3) Same-step semantics, for env i with terminated|truncated: reward, terminated, truncated, ticks and ep_* describe the finished episode's last transition; final_* hold its complete terminal observation (global + grid + mask); obs_* and mask hold the first observation of the next episode. For other envs, final_* and ep_* are stale. (4) Seeds: env i's k-th episode uses seed(i,k) = splitmix64(splitmix64(cfg.seed) ^ ((i as u64) << 32 | k as u64)). It does not depend on thread count or completion order and is reported in ep_seed. Held-out eval seeds have bit 63 set; training seeds never do. (5) In §3.7, replace `final_global=f32[N,G]` in the info dict with `done_idx=i64[k]`, `final_obs=dict(global_, grid, action_mask)` covering done rows only, and `episode_seed`. (6) The §9 Gymnasium wrapper sets `metadata['autoreset_mode'] = AutoresetMode.SAME_STEP` and maps final_obs to infos['final_obs'] / infos['_final_obs'].

**Rationale.** With only final_global, a value net that reads the grid can't bootstrap V(s_T) on max_days truncation. Gymnasium 1.4.0 (installed in the venv; checked sync_vector_env.py) puts the full observation of the finished episode in infos['final_obs'] in SAME_STEP mode, so §9's wrapper that 'passes env_checker' can't be correct with global-only finals. Without a seed schedule, episodes in episodes.jsonl can't be replayed. Seeds handed out in completion order would make datasets depend on rayon scheduling. Copying final_global for all N rows every step is 6 MB per call at N=1024, G=1500, although done rows are rare.

### 3. [must] §3.7 Python native module — VecEnv output buffers and GIL handling

**Change.** Keep §3.7's 'fresh arrays, callers may keep them' semantics but change the mechanism. (1) vec.step allocates the output arrays under the GIL: `PyArray::new` (uninitialised, every element written by write_obs/mask through the raw pointer as &mut [MaybeUninit<T>]), or `PyArray::zeros` to avoid unsafe at the cost of one memset. It then takes try_readwrite() → as_slice_mut() and fills them in place inside a single `py.detach(|| pool.install(...))`. It never steps into internal buffers and then copies out under the GIL. (2) Add `vec.step_into(actions, out: dict)`. It writes straight into caller arrays, e.g. `rollout.global_[t+1]` of a time-major [T,N,…] buffer, which is C-contiguous. It checks dtype, shape and C-contiguity, raising TypeError/ValueError on mismatch. (3) Accept actions as `PyArrayLike1<i64, AllowTypeChange>` and range-check them before detaching. A plain PyReadonlyArray1<i64> rejects int32. (4) Document that concurrent calls on one VecEnv raise `RuntimeError: Already borrowed`. VecEnv is an ordinary Send+Sync #[pyclass]; keep pyo3 0.30's default gil_used=false. (5) Move §3.7 after §3.6.

**Rationale.** Measured in the venv at N=1024 (G=1500 f32, 6×13×13 grid, 200-bool mask, scalars, final_global; 12.9 MiB): copying out of Rust buffers into fresh numpy arrays takes 548 µs per call, single-threaded with the GIL held. At 2M primitive steps/s a 1024-env call has a 512 µs budget, so copy-out alone at least halves primitive throughput (about 1% of a macro-mode call). Allocating fresh arrays instead costs +1 µs when the caller drops them (glibc reuses the block); when kept, the page faults spread across the pool threads. I compiled and ran this pattern against pyo3 0.30.1 + numpy 0.30.0, also as abi3-py311, so §3.7's abi3 wheel is viable. Results: (a) the GIL is released (a Python thread made 13.8M increments during a 300 ms call); (b) a concurrent second caller got RuntimeError: Already borrowed, not UB or a deadlock; (c) strided out views were rejected; (d) rollout[t] was filled in place; (e) fixed overhead was ≈5 µs (N=16) to ≈15 µs (N=1024); (f) int32 actions raised TypeError.

### 4. [must] §3.1 Config, §3.3 Primitive actions, §3.4 Macros, §3.6 Termination — time must advance

**Change.** (1) Add a tick-cost column to the §3.3 table and the rule 'every primitive advances game time by ≥ 1 tick': Select slot/tool, Eat, Open crafting menu, Menu option and Close menu = 1 tick; Wait = 10; Move = 1; masked = Wait(1). (2) §3.4: 'every macro consumes ≥ 1 tick even when it fails'. (3) §3.1: add `pub max_steps: u32`, defaulting to 100_000 in Primitive mode and 20_000 in Macro mode. (4) §3.6: '`truncated` at `max_days` or `max_steps`', and add a `step_cap` flag to the finished-episode info.

**Rationale.** Tick costs of actions 7–54 are unspecified. If any is 0, a policy can cycle Select-slot forever: the day never ends, max_days never fires, and per_day (−0.25) is never charged. PPO can discover that stalling beats a negative per-day return, a reward hack. Episodes become unbounded: lockstep batches never see done, the dataset gets runaway episodes, and the 'macro progress' test passes vacuously. A step cap also backstops future controller bugs that loop without advancing time.

### 5. [must] §2.4 / §3.2 / §3.5 — content tables and OBS_GLOBAL_DIM

**Change.** Replace 'embedded with include_str!' / 'parsed data tables' with compiled content. (1) crates/furrow/build.rs, with serde + toml as build-dependencies, parses data/*.toml and validates it: dangling ids, unobtainable requested items or missing recipe inputs fail the build. (2) It emits $OUT_DIR/content.rs containing: `pub const NUM_ITEMS, NUM_CROPS, NUM_LOCATIONS, NUM_MACROS, NUM_PRIMITIVES, OBS_GLOBAL_DIM, OBS_GRID_CHANNELS: usize`; static tables; typed ids (ItemId(u16), …); `pub const CONTENT_HASH: u64` (stable hash of the raw TOML bytes); and the JSON string returned by furrow.content_json(). (3) Every entity has an explicit, immutable `id = N` inside [[item]]-style arrays of tables. Ids are never derived from table-key order and are append-only across content versions; the build checks they are dense and unique. Macro ids are enumerated from these ids in a documented order. (4) Remixed mode changes only slot item identities, never wing, request or slot counts or k. If runtime parsing is kept instead, make it `pub fn obs_global_dim()` and still require explicit ids.

**Rationale.** A compile-time `pub const OBS_GLOBAL_DIM` can't be derived from TOML parsed at run time, so the contract is unimplementable as written. toml 1.2's Table is a BTreeMap (alphabetical), and it becomes an IndexMap if any crate in the graph enables preserve_order through feature unification (checked in the registry source). Ids taken from map order would silently renumber actions and obs offsets after unrelated edits or a dependency change, invalidating every dataset and checkpoint. Generated consts also allow fixed-size state arrays with no heap, move validation to build time, and remove parsing from new().

### 6. [must] §2.5 Determinism — determinism key and state hashing

**Change.** Replace 'Given (content version, EnvConfig, seed, action sequence) the trajectory is bit-identical across runs and platforms' with: 'Given (SIM_VERSION, CONTENT_HASH, EnvConfig, seed, actions), states, rewards, masks and step flags are bit-identical across runs, thread counts and platforms.' (1) `pub const SIM_VERSION: u32` is bumped by hand in any change to dynamics, macro controllers, pathfinding, RNG draw order or obs encoding. The golden test fails until goldens are re-blessed together with a bump. (2) Both values are recorded in meta.json and episodes.jsonl, and replay refuses a mismatch. (3) State identity is `GameState::stable_hash() -> u64`: an explicit little-endian field serialization (no usize, no #[derive(Hash)], no std DefaultHasher/RandomState) fed through an in-crate FNV-1a-64 or xxh64, with a checked-in test vector.

**Rationale.** Code changes alter trajectories without touching content, so recorded action logs and goldens would silently replay to different states. The rustc 1.99 std docs say DefaultHasher's 'internal algorithm is not specified, and so it and its hashes should not be relied upon over releases'. derive(Hash) also feeds usize length prefixes and isize discriminants, whose width depends on the platform. Goldens built on these break on a toolchain bump.

### 7. [must] §5 Trajectory format — per-step columns

**Change.** Replace `done u8[T]` and `days_to_go f32[T]` with three columns. (1) `flags u8[T]`: bit0 first step, bit1 terminated, bit2 truncated, bit3 executed action was exploration noise, bit4 macro partial/failed. (2) `expert_action i16[T]`: the expert's clean choice at that state, −1 if none. It differs from `action` in noise > 0 demos and in DAgger rows, where `action` is the learner's. (3) `ticks u16[T]`: game minutes consumed, for SMDP discounting γ^ticks. Alignment: row t = (obs_t, mask_t, action_t, reward_t = r(s_t,a_t), flags_t); the terminal observation is not a row. svrl.data derives days_to_go from `day` and the episode's `days`; it is NaN for unsuccessful episodes, which are excluded from time conditioning. meta.json adds sim_version, obs_layout_hash, the full env_config, seed_scheme and obs_global_dtype=f16. Keep f16 obs_global (all 1200 minute-of-day values stay distinct) and LE bit-packed masks (np.unpackbits(bitorder='little', count=A) round-trips; verified). svrl rounds live env obs through f16 at inference so training and serving inputs match.

**Rationale.** The DAgger stage (§6, §8) must store expert labels separately from the learner actions that were executed, and the format has no column for them. Noisy demos would teach BC to imitate random actions; the point of noise injection (DART) is to train on the clean label at the noise-visited state. `done` conflates termination with max_days truncation, and the value targets differ. days_to_go is undefined for failed runs and unknown until the episode ends. Macro steps last 1 to ~1200 ticks, so per-step discounting is wrong without `ticks`.

(2) Add `pyo3 = { version = "0.30.1", features = ["abi3-py311"] }` and `numpy = "0.30"` to [workspace.dependencies], without the `extension-module` feature: in pyo3 0.30 the PYO3_BUILD_EXTENSION_MODULE env var replaces it, and maturin sets it. ### 9. [should] §2.5 performance / §3.2 VecEnv scheduling / §3.4 macros / §8 pipeline

**Change.** (1) Each VecEnv owns a rayon::ThreadPool (num_threads, default available_parallelism) entered via pool.install, never the global pool. (2) Macro mode: `envs.par_iter_mut().zip(out.par_chunks_mut(G))…with_max_len(1)`. Primitive mode: `with_min_len(max(1, N/(8·threads)))`. (3) Add `EnvConfig.macro_max_minutes`, default 120. A macro that hits it returns MacroOutcome::Partial with no penalty and may be re-issued. This bounds per-step compute (target p99 ≤ 1 ms). (4) Workloads with no neural policy in the loop run episode-parallel in Rust: expert demos (furrow.generate_demos, the §8 collect_expert stage), DAgger relabel, expert and random baselines, obs materialization and benchmarks. Each rayon task runs one (Env, Expert) episode to completion into a thread-local buffer, and results are committed to the writer in episode-id order through a bounded reorder buffer. (5) Reserve lockstep VecEnv for neural-policy rollouts (PPO, eval).

**Rationale.** Measured on this Ryzen 7 9700X (16 threads, background load ≈3) with a heavy-tailed per-step cost mix: 60% 5–20 µs, 30% 50–300 µs, 9% 0.5–2 ms, 1% 3–8 ms. (a) Lockstep efficiency (work / threads·wall, with with_max_len(1)) was 11% at N=16, 23% at N=64, 46% at N=256 and 75% at N=1024. (b) The analytic perfect-scheduler bound max(Σ/threads, max cost) for this mix is 12/25/60/100%, so stragglers, not rayon, are the limit. (c) with_max_len(1) matched default splitting within noise at N ≤ 64 and beat it at N ≥ 256 (63 vs 68 ms; 79 vs 85 ms). (d) with_min_len(16) was 1.25–1.8× slower at N ≤ 256. (e) Capping per-step cost lifts the bound at N=64 from 25% to 61% (1 ms cap) or 86% (0.5 ms), and at N=256 from 60% to 100% (2 ms). (f) Episode-parallel runs have no barriers (≈100% efficiency), and ordered commit keeps datasets byte-identical across runs and thread counts.

### 10. [should] §2.5 Determinism and performance — enforce the rules with lints and tests

**Change.** (1) Add crates/furrow/clippy.toml and crates/furrow-expert/clippy.toml. They set disallowed-types = [std::collections::HashMap, std::collections::HashSet]. They set disallowed-methods for f32/f64 ln, ln_1p, log2, log10, exp, exp_m1, powf, powi, sin, cos, tan, hypot and cbrt, and for std::time::Instant::now and SystemTime::now. These stay allowed in build.rs, benches and furrow-cli via #[allow]. (2) Obs transforms use build-time tables: LOG1P_COUNT: [f32; 1000] and a log-money table indexed by integer magnitude. (3) Game probabilities are integers (chance_ppm(u32)). (4) Add crates/furrow/tests/alloc_free.rs with a counting #[global_allocator]. It asserts 0 allocations over 10k step + write_obs + mask calls after warm-up, for a single Env in each action mode.

**Rationale.** rustc 1.99's docs for f32::ln, and for 32 other float methods, state: 'The precision of this function is non-deterministic. This means it varies by platform, Rust version, and can even differ within the same execution'. §3.5's log-money and log1p/8 features therefore break the 'bit-identical across platforms' promise for observations, and for any golden that hashes them. The HashMap ban and the zero-allocation claim are prose today; as lints and tests they are checked on every PR.

### 11. [should] §5 / §8 — canonical record for Furrow data

**Change.** Add: for env=furrow, the action log is the source of truth. (1) Per episode it stores sim_version, content_hash, env_config, seed, action u16[T], expert_action i16[T], flags u8[T] and final_state_hash, about 5 B/step, as actions/ .npy files plus episodes.jsonl. (2) Observation shards are a derived cache keyed by obs_layout_hash. `furrow traj materialize <ds>` builds them by episode-parallel replay and asserts each final_state_hash. collect_expert writes both in one pass. (3) In DAgger rounds Python records only the learner's actions; `furrow traj relabel` replays them in Rust and fills expert_action. (4) SDV datasets always store observations, since they can't be replayed.

**Rationale.** Observation rows cost ~3–4 KB/step versus ~5 B for actions, and the §3.5 layout will change many times. With logs, a layout change means re-materializing by replay, which is faster than re-running the expert planner. Lockstep collection would otherwise buffer whole episodes of observations per env before it can write contiguous episodes: 256 envs × 5k steps × 4 KB ≈ 5 GB. Goldens, crash repros and dataset sharing all become small (seed, actions) files, which is exactly what the determinism contract makes replayable.

### 12. [should] §2.2 World / §2.5 — state memory layout and time advance

**Change.** (1) GameState keeps every location's tiles, plus the current mine floor, in one contiguous per-env arena of SoA planes: terrain u8, obj_kind u8, obj_data u16 (item id, stage, HP or slab handle), soil u8 flags and crop_stage u8. A passability bitset is updated incrementally. (2) Crops, machines and forage live in fixed-capacity slabs sized by content consts and addressed by u16 handles. Backpack, skills and tools are fixed arrays. (3) Nothing grows after new(): reset regenerates in place, and Env: Clone is about one arena memcpy. (4) Time is event-driven. Timers are absolute minute stamps (ready_at, upgrade_done_at). advance(minutes) handles only events due in the interval (shop open/close, machine ready, 02:00 pass-out, 06:00 spawns), so per-tick work is O(1) with no per-tick scans of crops or machines. Overnight processing is one linear pass over the soil planes.

**Rationale.** With SoA planes the egocentric grid write is 6 channels × 13 clipped row copies, well under 1 µs, and stable_hash is the arena hash plus scalars. About 7k tiles gives ≈40–60 KB per env, ≈250 MB for 4096 envs, so a step's working set fits the 1 MB per-core L2. A cheap Clone gives snapshot/restore for replay checkpoints, DAgger branch rollouts and expert lookahead. Macros walk tick by tick through step_primitive, so any per-tick entity scan multiplies the cost of every walk and would sink the 2M primitive steps/s target.

### 13. [should] §3.4 Macro action space — pathfinding

**Change.** Replace '(with A* pathfinding across the world graph)' with the following. (1) Routing between locations uses a next-hop warp table computed once per content version (the topology is static). (2) Within a location: 4-neighbour A* with a Manhattan heuristic and a binary heap, over per-env scratch buffers. g/parent/visited use generation stamps, so a search clears nothing and allocates nothing. (3) Multi-target macros (WaterCrops, Harvest, Forage, ClearField, MineFloor, LoadMachines) pick the next target with one early-exit BFS from the player, or a boustrophedon sweep over rectangular plots, never one A* per candidate. (4) Optional per-env distance fields per (location, POI) are built lazily and invalidated by a per-location walk_version counter. (5) Nothing is precomputed in reset, and no cache is shared across envs.

**Rationale.** Layouts are procedural per seed, so distance fields can't be global. Flooding ~30 POIs × ~1.7k cells eagerly costs on the order of 0.5 ms, about 10× the 50 µs reset budget. One A* per crop or rock is O(targets × cells) per macro, which is the source of the heavy tail measured in the scheduling amendment. A shared cache needs locks and lets eviction order leak into outcomes.

### 14. [should] §2.5 Determinism — RNG streams

**Change.** Replace 'Streams: world (layout, merchant stock, weather) and dynamics, both derived from the episode seed' with: 'Exogenous randomness (layout, weather, forage spawns, merchant stock, mine floors, daily fish tables) never comes from a long-lived stream. Each event seeds a fresh PCG32 from mix(episode_seed, DOMAIN_TAG, day[, location|floor]). Only outcomes of agent actions (catches, drops, yields, skill doubling) use the per-env dynamics stream, which lives in GameState and is covered by stable_hash. Two policies on the same seed therefore face identical weather, forage and merchant sequences.'

**Rationale.** With a sequential world stream, any action-dependent number of draws desyncs every later exogenous event. For example, forage spawned 'up to a cap' depends on what the player picked up. Evaluation then loses common random numbers: paired learner-vs-expert comparisons on held-out seeds need far more seeds, and DAgger counterfactuals see different futures. Mines already use the keyed form (seed, day, floor); this generalizes it at no cost.

### 15. [should] §11 Quality bar — test suites

**Change.** Replace the 'Furrow tests include' bullet with these suites. (a) Goldens in crates/furrow/tests/golden/*.json: sim_version, content_hash, cfg, seed, actions, stable_hash every 256 steps, final hash and return. A failure reports the first diverging checkpoint. FURROW_BLESS=1 rewrites them, and the test fails if goldens changed without a SIM_VERSION bump. (b) proptest over seeds × random valid action sequences (≤ 2k steps, both modes). It checks: energy ∈ [0, max]; money ≥ 0; stacks ≤ 999; ≤ 24 slots; player on a passable tile; time strictly increases each step; an item-conservation ledger; a masked primitive only advances 1 tick; clone-then-step equals step (by hash); reset(s) equals new(cfg{seed: s}). (c) VecEnv versus serial Env: N=37 envs × 1k steps at 1 and 16 threads produce byte-identical outputs to N independent Envs. Auto-reset obs equals a fresh reset(seed(i,k)), and final_* equals the pre-reset write_obs. (d) Macro expansion: log the primitives a macro issues, replay them in Primitive mode, and require an identical hash. (e) Test vectors for SplitMix64, PCG32 and below(). (f) alloc_free.rs. (g) pytest: dtype, shape and contiguity errors; fresh-array semantics; GIL release (a background thread progresses during a long step); the concurrent-call RuntimeError; an RSS-stable 1e5-step leak check; gymnasium env_checker plus SAME_STEP final_obs. (h) Nightly in release: expert ≥ 95% on 200 seeds, 100k proptest cases, a bench smoke run.

**Rationale.** The current bar covers only determinism, content, macro progress, the expert and benches. It misses the usual failure classes of vectorized simulators: buffer offset and aliasing bugs, scheduling-dependent results, auto-reset off-by-one errors, and silent drift in dynamics between versions. Hash checkpoints turn 'golden failed' into 'diverged at step 4352', which can be bisected.

### 17. [should] §2.5 Targets + Cargo profiles + benchmark methodology

**Change.** Replace 'Targets (16-core desktop, release build): …' with the following. (1) Machine and build: the dev box (AMD Ryzen 7 9700X, 8C/16T, 32 MB L3), 16 pool threads, and profile.release with lto = "fat", codegen-units = 1 and panic = "unwind" (needed so PyO3 turns panics into exceptions). (2) Primitive: ≥ 2M steps/s aggregate at N=1024 with random valid actions, including obs and mask writes. (3) Macro: ≥ 20k steps/s aggregate replaying the golden expert action logs (the expert's state distribution), and per-macro-kind p99 ≤ 1 ms. (4) reset p99 ≤ 50 µs, and 0 allocations per step. (5) `furrow bench` reports steps/s at 1/2/4/8/16 threads, per-call p50/p99, per-macro-kind histograms, RSS per env, and the Python-loop rate of VecEnv.step. (6) Method: fixed seeds, 2 s warm-up, ≥ 5 runs of 10 s, median plus min/max, and the system load recorded. Absolute numbers are never a CI gate. (7) criterion 0.8 micro-benches: step per macro kind, write_obs, mask, A*, reset. (8) Add [profile.profiling] with inherits = "release" and debug = "line-tables-only".

**Rationale.** This machine has 8 physical cores, not 16, and SMT gives well under 2×. Random macro streams rarely reach expensive late-game states (many crops and machines, deep mines), so they overstate throughput; data generation runs on the expert's state distribution. The box runs other jobs (load ≈3 during this review), so a single run is noise. The hot loop crosses crates (furrow → furrow-expert → furrow-py), where fat LTO with one codegen unit often pays.

### 18. [should] §1 Repository layout — crate boundaries

**Change.** State the boundaries explicitly. (1) `furrow` contains GameState, Env, VecEnv and the generated content, with rayon behind a default `parallel` feature. (2) `furrow-traj` has no in-tree dependencies: schema, .npy writer/reader, memmap2 and half. The SDV converter and svrl share it. (3) One episode-parallel runner (generate, relabel, materialize, evaluate) lives in furrow-expert::runner, or in a new furrow-gen crate built on furrow, furrow-expert, furrow-traj and rayon. furrow-cli and furrow-py's generate_demos both call it; neither reimplements the loop or the seed scheme. (4) sdv-bridge uses one OS thread per game connection, so blocking I/O never runs on rayon workers, and it depends only on furrow-traj. (5) Workspace deps add pyo3, numpy, memmap2, half, proptest (dev) and criterion (dev), and drop zip.

**Rationale.** The contract names VecEnv but not its crate, and furrow has no rayon dependency today. §3.7 exposes generate_demos and the CLI has a demos command. Without a shared runner each grows its own parallel loop and seed derivation, which is an easy place for determinism to diverge. Keeping furrow-traj free of furrow is what lets real-game recordings share the format.

### 19. [could] §3.2 action_mask / write_obs, §3.5 grid payload channel

**Change.** (1) `pub fn action_mask(&self) -> &ActionMask` returns a bitset ([u64; ⌈A/64⌉]) computed once at the end of reset/step and cached; step needs it anyway to validate the incoming action. It offers write_bools(&mut [bool]) and write_packed_le(&mut [u8]), the latter in the trajectory layout. (2) Macro predicates are conservative O(1) checks on maintained summaries: per-location forage counts, per-shop 'reachable before close' computed once per step from the warp table, and held ∩ open-slot counts. Budget ≤ 2 µs per env. (3) Restate the mask rule as 'masked ⇒ never executed; unmasked ⇒ advances ≥ 1 tick, possibly returning MacroOutcome::Failed', and have bench report macro_fail_rate. (4) Change the signature to write_obs(&self, global, grid: Option<&mut [u8]>). (5) The grid payload channel becomes a dense u8 'tile-visible id' generated at build time (the build fails above 255), instead of the id's low byte.

**Rationale.** 'Cannot make progress ⇒ masked' can't be decided without simulating the macro. With ~200 macros × N envs, a mask computed twice per step could cost as much as the step itself. Low-byte ids alias in the grid (item 3 and item 259 look the same).

### 20. [could] §4 Expert planner — reproducible, non-privileged labels

**Change.** Add: (1) Expert randomness (noise and style draws) is counter-based, keyed by (expert seed, episode seed, step index). act() and vec.expert_actions() are then pure functions of (state, keys): repeated queries return the same action and never shift a stream. (2) The expert reads only state the agent can observe, plus content. (3) Add a test that perturbing unobservable state (future-day RNG keys, unvisited mine floors, weather beyond the forecast) leaves act() unchanged.

**Rationale.** Replay-based relabel and §3.7's lockstep vec.expert_actions(noise=…) both query the expert at states where its action may not be executed. A stateful noise RNG would make labels depend on query history. A privileged expert that knows seed-derived futures creates an imitation gap that BC and DAgger can't close.

### 21. [could] §3.7 Python native module — long calls, panics, future async API

**Change.** (1) generate_demos, relabel and materialize run in chunks and call Python::attach(|py| py.check_signals()) between chunks so Ctrl-C works. (2) A panic inside VecEnv.step is converted to an exception and poisons the VecEnv: later calls raise until reset(). The exception carries a repro bundle: env index, episode seed, sim_version, and the episode's action log, which each env keeps in a preallocated Vec<u16>. (3) Keep every buffer indexed by env id so an EnvPool-style send(actions, env_ids) / recv(min_batch) can be added later without breaking the API.

**Rationale.** A detached multi-minute call otherwise ignores SIGINT. After a panic mid-batch, some envs have stepped and others haven't, so continuing silently corrupts rollouts. A crash in env 873 after hours of training can only be debugged from its (seed, actions).
