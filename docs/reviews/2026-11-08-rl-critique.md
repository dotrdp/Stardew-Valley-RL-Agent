# RL-researcher critique of DESIGN.md v1 (2026-11-08)

Produced by an independent review agent; amendments are folded into DESIGN.md v2.

## Summary

Review of /home/rd/code/Stardew-Valley-RL-Agent/docs/DESIGN.md. Another agent edited the file during the review: it added §3.7 (Python API), §8 (pipeline), §9 (Gymnasium and NeMo Gym) and §10 (papers), and moved the quality bar to §11. The amendments below use the current numbering. Every crate is a one-line stub and python/ is empty, so all of these changes are cheap to make now. I modified no files.

Verdict: the overall approach is right for this goal: a fast deterministic sim of original content, a macro action space, a scripted expert that decides from the current state (so it can be queried for DAgger), then BC/DT → DAgger → PPO with a KL penalty. As written, though, the contract would probably produce a policy that imitates poorly and an RL stage that optimizes the wrong objective, and the results would be hard to defend. The main risks, in order:
1. Reward and discount. The contract never sets γ. A per-decision γ lets the agent profit from inserting extra decisions to push day penalties away, which has nothing to do with the metric. Raw progress rewards (plausibly 150–250 for SDV-scale content) dwarf the speed signal: a 20-day improvement is worth 5. So ranking by return is not ranking by completion day.
2. The expert reads full GameState on procedurally generated maps. Anything it uses beyond the observation (travel times, per-tile crop timers, hidden spawns, multi-day weather) cannot be learned, and DAgger then adds labels the learner cannot predict.
3. The observation is not item-centric. Per-slot flags and a request×item multi-hot are about 8.4k dims versus about 0.9k, and their meaning changes under Remixed. Time is also scaled by max_days, so changing the cap shifts the input.
4. Macro semantics are underspecified: Buy is indexed by menu row and buys one pack, ClearField and Chop have no time limit, there are no Till or place-machine macros, Deliver's matching is unspecified, and several decisions take zero game time.
5. The trajectory format drops the terminated/truncated distinction, elapsed time, clean expert labels and each episode's final observation.
6. There is no BC→PPO protocol: no critic warm-up, no frozen normalizer, no rule that action masks apply in the update, no kickstarting toward the expert.
7. The installed Gymnasium (1.4.0) defaults vector envs to NEXT_STEP autoreset and rejects SAME_STEP in its observation wrappers. The native VecEnv resets in the same step, so it must declare that.
8. There is no evaluation protocol (seed splits, censored metric, paired seeds), no baseline list and no canonical datasets.

Feasibility: macro mode is about 15–30 decisions per day, so 1–6k decisions per episode. At the 20k decisions/s target that is about 36k env-only episodes per hour, enough for PPO finetuning on CPU. PPO from scratch will probably fail on season-scale credit assignment. Primitive mode (about 1e5 decisions per episode) is not a viable RL track. The NeMo/LLM track at full-episode granularity costs 3–6M prompt tokens per episode and needs segment tasks instead.

Of the 19 amendments, 11 are 'must'. The two most consequential are the reward/discount fix and the expert information contract.

## Amendments

### 1. [must] §3.1 RewardConfig, §3.2 Step, §3.6 Reward and termination, §3.7 cfg/step returns

**Change.** Replace RewardConfig with a speed-only reward plus potential-based progress, discounted per in-game day: RewardConfig { per_day: f32 = -1.0 (charged at every day end, whether by Sleep or pass-out; return unit = days), completion: f32 = 0.0, phi_slot/phi_request/phi_wing: f32 (progress potential Φ(s), scaled so Φ_max ≈ the expert's mean completion days), shaping: bool = true (r += γ_day^day_ends·Φ(s′) − Φ(s); Φ is not zeroed at termination), gamma_day: f32 = 0.99 (horizon ≈ 100 days; never below 0.97; learners must use the same value) }. Add day_ends: u8 to Step and to env.step/vec.step (§3.7). Redefine ticks as absolute in-game minutes elapsed, including skipped night. New §3.6 text: 'Discounting is per in-game day, never per decision. A transition that crosses day_ends day boundaries is discounted by γ_day^day_ends (=1 within a day). GAE, IQL/TD targets, DT returns and critic warm-up all use this. With per_day < 0, completion ≥ 0 and potential-based progress, the expected discounted return is an increasing affine function of E[γ_day^T] (T = completion day), so the optimum is pure speed. Raw per-slot/request/wing rewards and costs per simulated tick are not allowed.' The old per_slot/per_request/per_wing values survive only as potential weights.

**Rationale.** The contract fixes no γ, so ppo.py will default to a per-decision γ. Value then depends on the number of macros, not days. With about 25 decisions per day, a completion bonus of 50 at day 60 is worth 11 at γ=0.999 and 1e-5 at γ=0.99. Worse, whenever the continuation value is negative the agent gains by inserting extra decisions (Wait30 chains, one-pack Buys, passing out instead of sleeping) to push future day penalties away. Raw progress rewards, plausibly 150–250 in total, dwarf the speed signal (a 20-day improvement is worth 0.25·20 = 5). So RL can trade completion time for early easy slots, for example foraging for slot rewards instead of planting season-gated crops. Potential-based shaping keeps the dense credit but provably leaves the optimum unchanged (Ng et al. 1999; for SMDPs and options, Gao & Toni 2015): G = −c/(1−γ) + γ^T(c/(1−γ) + B + Φ_max) − Φ_0. A cost per simulated tick would reward sleeping early.

### 2. [must] §4 Expert planner (+ §3.7 expert_action, §11 tests)

**Change.** Add to §4: '(a) Information contract: decision rules read only the §3.5 observation (f32, before f16 quantization) and static content tables. Implement them against an ExpertView built from write_obs output. Anything else the expert needs is added to the observation first. Full GameState access is allowed only inside macro controllers on the env side. (b) Statelessness: Expert::new(cfg).act(env) returns the same action as a long-running instance on any state; test on 1e5 states from noise=0.3 rollouts and from DAgger rollouts. (c) Recovery: expert takeover from states at uniformly random days of noise=0.3 rollouts succeeds ≥90% of the time; report the extra days. (d) The ≥95% success bar applies to Fixed and to Remixed. Content validation rejects or resamples a Remixed list if its static critical-path lower bound (season windows, growth days, unlock dependencies) exceeds max_days − 24 or the expert fails it. (e) Noise uses a private RNG stream, never the world or dynamics streams. (f) Expert::act ≤100 µs p50 in release builds; vec.expert_actions labels all envs in parallel. (g) DAgger: β_i = 0.5^i, at least 8 rounds, aggregate all rounds, report the score after every round.' In §3.7, split expert_action(noise, style) into expert_action(style) -> int (the clean label) and noisy_expert_action(noise, style) -> (executed, clean).

**Rationale.** The expert reads full GameState, but maps are laid out procedurally per seed. Travel times, exact per-tile crop timers, multi-day weather, hidden spawns and ladder positions are not in the observation. Decisions conditioned on them cannot be learned from observations. This is the imitation gap of privileged experts (Weihs et al. 2021; Swamy et al. 2022), and DAgger makes it worse by adding labels the learner cannot predict, so the policy averages over them. DAgger labels are valid on learner-visited states only if the expert is stateless and recovers from off-plan states such as a missed season or a wrong upgrade. A scripted planner tuned on its own trajectories often does neither. Claims about Remixed need an expert that solves Remixed and request lists that are feasible. The §3.7 API currently returns the executed noisy action as if it were the label.

### 3. [must] §3.5 Observations

**Change.** (a) Replace 'restoration state (per slot delivered flag, per request/wing done flags, request→item requirement multi-hot)' with item-centric features whose shapes depend only on content and are identical in Fixed and Remixed. Per item i: need[i] = units still required by open requests (a k-of-N request counts each candidate until k are filled; /16, clipped), cover[i] = min(held, need)/need, n_open_slots[i] (scarcity). Per request: filled/k, done flag, remaining coin amount /1e4. Per wing: done flag. (b) Add eta[poi], the travel minutes from the player to every macro-target POI, from cached per-POI distance fields, /600. Also add: opens_on_arrival[shop]; free backpack slots; free tilled and tillable tiles per field (farm, greenhouse); per crop, the planted/watered/ready counts, the minimum days-to-ready and how many mature before season end; days left in the season; pending crate value; unlocked-recipe flags; current mine floor; last_macro_failed. (c) Scale only by content constants: 'days elapsed / max_days' becomes 'days elapsed / 384'; money becomes log1p(money)/log1p(1e6) plus min(money, 1e4)/1e4. No feature may depend on EnvConfig. (d) Macro mode gets EnvConfig.grid: bool, default false. When true, final_obs includes the grid. Grid on is an ablation.

**Rationale.** Every macro decision turns on what is still needed, how much, and how far away it is. Item-indexed demand lines up one-to-one with the item-indexed macros (Buy, Plant, Forage, Fish, Craft) and keeps its meaning under Remixed, where slot-position flags change meaning on every seed. A request×item multi-hot is about 7.5k sparse dims for plausible content (30 requests × 250 items): roughly 8.4k instead of 0.9k global dims, or 34 GB instead of 3.5 GB per 1,000 f16 episodes. ETAs close the seed-dependent travel-time gap for time-window decisions: shop hours, fish windows, getting home before 02:00. A feature scaled by max_days shifts silently when PPO or evaluation uses a different cap. At macro boundaries, the egocentric grid shows a seed-specific patch near wherever the last macro ended. It has no decision value, gives the policy something to overfit, costs 1 KB per step, and complicates bootstrapping.

### 4. [must] §3.4 Macro action space (+ §11)

**Change.** Replace the enumeration paragraph with normative semantics: '(i) Ids are a pure function of the content version, sorted by (kind, entity id) and listed in meta.json. They never depend on seed, RestorationMode, season or current stock. POI sets (fishing spots, counters) are defined by content; procedural layout only moves them. (ii) Buy(shop, item, q) with q ∈ {1, 5, 25} packs, enumerated over the union of all stock tables including the full merchant pool. It is masked when the item is not stocked, unaffordable or there is no space, and is never indexed by menu row. (iii) Plant(seed, Farm|Greenhouse) tills as needed and plants all held seeds of that kind in a fixed tile order. (iv) Craft(recipe) crafts one; machines are placed automatically on the next free farm pad. (v) ClearField, ChopWood, ChopHardwood, Forage, Fish, MineFloor and MineDescend are time-boxed (≤60–120 min) and stop early when done. (vi) Deliver assigns held items to open slots by a deterministic max-matching: maximize completed requests, and prefer items that are candidates for fewer other open slots. Coin requests are paid only through a new PayCoins macro, masked unless affordable. (vii) LoadMachines, ShipSurplus and Eat never consume items that the shared reservation function marks for open requests.' Add two tests to §11: re-executing the expert's macro ids through Env::step reproduces its trajectory bit-identically; the canonical expert averages ≤40 decisions per day.

**Rationale.** These semantics decide whether the expert's plan can be written in macros at all, how long the horizon is, and whether an action id means the same thing across states and seeds. Menu-row or stock-dependent ids change meaning per visit. That makes action semantics nonstationary and breaks Remixed generalization and dataset reuse. One-pack Buy turns buying 40 seeds into 40 near-identical decisions, which lengthens the horizon and pushes BC toward copying the previous action. An untimed ClearField or ChopWood can irrevocably burn a day in one decision, which removes the within-day control RL needs to beat the expert. A greedy Deliver can spend a scarce item where a common one would do, and the learner never sees why. Planting needs tilled soil, yet there is no Till macro and no way to place a crafted machine.

### 5. [must] §5 Trajectory format (+ §3.7 generate_demos)

**Change.** Replace done u8[T] with terminated u8[T] and truncated u8[T]. Add: day_ends u8[T]; ticks u16[T] (absolute minutes elapsed in the step); expert_action i32[T] (the clean expert action at this state, −1 when unavailable, e.g. for human data); actor u8[T] (0 expert, 1 injected noise, 2 learner/DAgger, 3 human); progress u16[T,3] (slots, requests and wings after the step); macro_failed u8[T]; and optionally expert_intent u8[T] (which §4 priority rule fired). Per episode, add final_obs_global (the observation after the last action) in final_obs.npy [E, G], aligned with episodes.jsonl. meta.json gains reward_config, gamma_day and seed_range. Define days_to_go = completion_day − day only for successful episodes, and NaN for failed ones (consumers choose a censoring rule). generate_demos records both the executed and the clean action.

**Rationale.** done conflates success with timeout, so offline RL and critic pretraining bootstrap wrongly. Per-day discounting cannot be reconstructed without day_ends. Noisy and DAgger data help only when trained on clean labels at the states the noise or the learner reached (DART, Laskey et al. 2017; DAgger). expert_action lets one format hold expert demos, DART data, DAgger data and human data. Without the final observation, the last transition of every truncated episode has no target. Progress counters let rewards be recomputed for RewardConfig sweeps and shaping ablations without regenerating data. Intent labels enable hierarchical BC, which improved BC substantially in NetHack (Piterbarg et al. 2023). For a failed run, days_to_go = max_days − day falsely claims completion at the cap.

### 6. [must] §6 Algorithms + §8 stage 6 train_ppo

**Change.** Add a normative 'Finetuning protocol' paragraph: '(1) Observation normalization uses the BC normalizer, frozen. Never use gymnasium NormalizeObservation/NormalizeReward or re-estimate statistics online. (2) Actor and critic do not share a trunk, or critic gradients stop at the shared trunk. (3) Critic warm-up: initialize the value head by regressing on day-discounted dataset returns, then train only the critic on rollouts of the frozen BC policy until explained variance ≥0.8 or for 20 iterations, whichever comes first. Only then start actor updates. (4) The rollout buffer stores masks; new log-probs, ratios, entropy and KL all use masked logits. (5) Regularize with KL(π_θ‖π_BC) on visited states with an annealed coefficient, and/or a decaying kickstarting cross-entropy toward vec.expert_actions on visited states (Schmitt et al. 2018). Train BC with label smoothing ≈0.02 or calibrate its temperature on validation so the initial policy is not deterministic. (6) GAE: δ_t = r_t + γ_day^{day_ends_t}·V(s_{t+1})·(1 − terminated_t) − V(s_t), with s_{t+1} = final_obs on truncation; cut the recursion at every episode end; λ ≈ 0.98 per decision. max_days is a compute cap, not part of the objective, so PPO may train with a shorter cap (bootstrapped) without changing observations. (7) Fixed reward scale (unit = days, value targets /100); no running reward normalization. (8) Log the evaluation score before the first actor update and after every iteration. A drop of more than 10% at iteration 1 means a protocol bug.'

**Rationale.** BC→PPO finetuning typically fails by collapsing early. The causes are an untrained critic producing garbage advantages, re-estimated normalizers shifting the inputs, and value gradients wrecking a shared pretrained trunk (Uchendu et al. 2023, Jump-Start RL). Finetuning also forgets skills in states it does not revisit early (Wołczyk et al. 2024, NetHack). Season-start planting and tool-upgrade decisions are exactly those rare states: a KL on visited states does not protect them, while kickstarting toward the queryable expert does. Leaving masks out of the log-prob in the update is a common silent bug. BC on a deterministic expert yields near-one-hot logits, so PPO has nothing to explore. Running reward normalization silently rescales the KL weight. Gymnasium 1.4's vector NormalizeObservation updates its running statistics online by default.

### 7. [must] §3.2 VecEnv auto-reset, §3.7 vec.step, §9 FurrowVecEnv, §11

**Change.** In §3.2 and §3.7, vec.step info returns final_obs as the full dict {global_, grid, action_mask} instead of only final_global, plus final_day_ends. Every step returns day_ends and ticks alongside reward, terminated and truncated. VecEnv(seed_range=(lo, hi)) draws auto-reset seeds only from that range; an eval mode takes an explicit seed list and does not auto-reset. In §9, FurrowVecEnv declares metadata['autoreset_mode'] = gymnasium.vector.AutoresetMode.SAME_STEP and exposes info['final_obs'] and info['_final_obs'], following the Gymnasium 1.x convention. Add a §11 test: on a scripted rollout with known rewards, GAE targets match hand-computed values for both terminated and truncated endings, across an auto-reset boundary.

**Rationale.** The installed Gymnasium (1.4.0) defaults vector envs to NEXT_STEP autoreset, reads metadata['autoreset_mode'], and its VectorObservationWrapper subclasses raise on SAME_STEP. The native VecEnv resets in the same step (§3.2). If the mode is not declared, wrappers and third-party PPO code (CleanRL/SB3 style) assume the other convention. They then bootstrap across episode boundaries or treat the reset observation as the next state, a bias that never crashes. Truncation is not termination (Pardo et al. 2018). Bootstrapping a truncated step needs the final observation in every input the critic uses, plus that step's discount. Unrestricted auto-reset seeds can leak test seeds into training.

### 8. [must] §3.3 Primitive actions, §3.4 Macros, §11 'macro progress' test

**Change.** Add: 'Every step advances the absolute clock. Primitives cost ≥1 tick, including Select, Eat, Menu and Close. Macros cost ≥5 ticks even when they fail. A day accepts at most max_decisions_per_day macro decisions (default 64); after that only Sleep is unmasked. Stepping a masked macro = Wait(10 min) with info invalid_action=1. An unmasked macro that fails partway returns macro_failed=1 and charges its elapsed time. Masks are cheap preconditions computed with ETAs: shop open on arrival, affordable, space, inputs held.' Replace the §11 macro-progress test with: '≥99% of unmasked macros on states from noisy rollouts make progress beyond the clock; the rest set macro_failed'.

**Rationale.** In this genre, menus, buying, crafting and eating take zero game time. With one-pack Buy, Craft, Ship and Eat as separate decisions, a policy can emit unlimited decisions while the clock stands still. Rollouts and evaluations hang, days never end, and under any per-decision discount this becomes an exploit. Exact 'cannot make progress' masks are impossible for macros whose outcome depends on paths and time, so failure has to cost time and be visible.

### 9. [must] §6 Evaluation, §2.5 Determinism, §8 stages 6–7

**Change.** Replace the §6 Evaluation bullet with: 'Seeds: train [0, 2^32), validation [2^32, 2^32+1000), test [2^33, 2^33+1000). Model selection, including §8's best imitation policy, uses validation only; test is used once per reported number. Primary metric: censored completion day C = completion day if successful, else max_days. Report mean, median, IQM and CDF over the 1,000 test seeds, plus success rate. Speed score S = (max_days − mean C_agent)/(max_days − mean C_expert): 0 = never finishes, 1 = expert, >1 = faster than expert. All policies run on the same test seeds; report the per-seed paired difference against the expert with a 95% bootstrap CI. Use ≥5 training seeds per method with rliable-style CIs, and report both greedy and sampled decoding. Also report missed seasonal-window events and wings-done-versus-day curves. Tiers: (1) Fixed, held-out seeds; (2) Remixed, held-out seeds; (3) Remixed-OOD, a held-out partition of the per-request pools (RemixPartition::{Train, Test}).' Add to §2.5: 'World randomness (layout, weather, forage spawns, merchant stock, mine floors) is drawn from counter-based streams keyed by (seed, day, purpose[, location, floor]). It is independent of the policy's actions, so every policy faces the same world on a given seed.'

**Rationale.** Mean days over successes alone has survivor bias. Missing a seasonal window costs about 96 days, so completion days are bimodal, and means mislead without CDFs and IQM (Agarwal et al. 2021). Seed difficulty (weather, merchant luck, layout) likely dominates the variance. Pairing seeds removes most of it, but only if world draws do not depend on how many RNG calls the policy triggered, for example merchant stock rolled per visit. Choosing the best imitation policy on held-out evaluation seeds leaks the test set. Fixed mode with new seeds mostly re-tests the same task, so generalization claims need the Remixed tiers.

### 10. [must] §6 Algorithms/Evaluation (baselines and budgets)

**Change.** Add: 'Required rows: masked-uniform random; the expert with its canonical style, and the best of its styles; BC on expert data; naive BC on noisy data with executed labels versus BC+DART with clean labels; DAgger; filtered BC (fastest 10% and 25% of episodes); time-conditioned BC/DT; IQL (discrete actions, per-day discount) representing offline RL; PPO from scratch with the same reward; PPO from BC and from DAgger (the headline result). Each row states its track and budget. Track O (offline): canonical datasets only, a fixed number of gradient steps. Track I (interactive): ≤1e6 expert labels. Track R (RL): ≤2e8 environment decisions on train seeds.'

**Rationale.** Without filtered BC and plain BC on expert data, any DT gain cannot be interpreted: filtered BC often matches DT (Chen et al. 2021; Emmons et al. 2022). Without PPO from scratch, the value of demonstrations is not shown. Without an offline-RL row, the claim 'learn primarily from (suboptimal) trajectories' lacks its standard comparison. In Furrow, expert data is effectively unlimited (about 36k env-only episodes per hour), so results mean little unless offline, interactive and RL budgets are separate and fixed. Separating them also mirrors the data-scarce SDV setting.

### 11. [must] §6 (new 'Datasets' bullet), §8 stage 1 collect_expert

**Change.** Define versioned canonical datasets, produced by collect_expert from the train seed range: fixed-expert (noise 0, canonical style, 1,000 episodes); fixed-styles (noise 0, 8 styles, 1,000 episodes); fixed-dart (noise ∈ {0.05, 0.1, 0.2} with clean labels, 1,000 episodes each); fixed-mixed (the union of the above plus noise 0.3 and 0.5, for DT and offline RL); remixed-expert (5,000 episodes); and nested subsets of 25, 100 and 400 episodes for data-scaling curves. Pin each dataset by content_hash plus a manifest of (seed, generator) pairs.

**Rationale.** The contract defines the generator's noise and style settings but no datasets. Without a fixed composition and fixed seed ranges, results are neither reproducible nor comparable across the two planned papers. DART-style noise with clean labels is the cheapest way to cover recovery states. A mixed-quality set is needed to test whether DT or offline RL can extract a faster-than-average policy. A data-scaling curve is the most informative single imitation result. At about 0.9k f16 dims and 2k decisions per episode, 1,000 episodes is about 3.5 GB.

### 12. [should] §3.2 Env, §4 Expert (headroom and cost-sensitive labels)

**Change.** Require Env: Clone: a cheap snapshot whose continuation is bit-identical, with a test in §11. Add furrow_expert::cost_to_go(env, action, n_dyn_seeds) -> f32, the mean completion day when taking the action and then following the expert, using the same dynamics seeds for every action compared. Use it to (a) report a rollout-improved expert, π′(s) = argmin_a Q^E(s, a), which is never worse than the expert (Bertsekas rollout), as the headroom reference for PPO; and (b) produce cost-sensitive imitation labels (AggreVaTe, Ross & Bagnell 2014) at sampled states, such as the first decision of each day and every season-start day.

**Rationale.** BC and DAgger weight all mistakes equally. In a speedrun, a handful of decisions (season-start planting, tool upgrades, merchant days) dominate completion time, and a missed window costs a whole season. Cost-to-go labels let the learner weight those decisions. The rollout-improved expert measures how much headroom over the expert the macro space actually allows. Without that number, a PPO gain of N days cannot be interpreted, and if there is no headroom, no gain will appear. Requiring Clone now is cheap; retrofitting it after caches and thread pools exist is not.

### 13. [should] §6 Models/Algorithms (time-conditioned imitation)

**Change.** Specify: '(1) Condition only on successful episodes, or add a success token with a censored target (max_days − day + 96) for failures. (2) Also store days_to_go_expected: the mean completion day over 4 re-runs of the same (seed, generator) with different dynamics seeds, minus the current day. Compare conditioning on realized versus expected targets. (3) Test-time target: the q-quantile of training completion days for q ∈ {0.05, 0.25, 0.5}, decremented at each day end and clipped at ≥1; report the full q sweep. (4) Scale days_to_go by a constant (/384). (5) Ablate the prev_action token, and report MLP-BC with the same conditioning input.'

**Rationale.** Realized days_to_go mixes skill with luck (weather, merchant stock, fish and drop RNG). Return-conditioned imitation then learns to act as if lucky and fails in stochastic environments (Paster et al. 2022; Yang et al. 2022; Brandfonbrener et al. 2022). Targets below the data minimum are out of distribution, and DT rarely extrapolates past the best returns in its data, so beating the expert has to come from RL or search. Previous-action tokens cause copycat failures in BC (Wen et al. 2020; de Haan et al. 2019), especially with repeated macros. The observation is close to Markov, so history adds little.

### 14. [should] §6 Data (sampling and style)

**Change.** Replace 'uniform step sampling' with episode-balanced sampling: pick an episode uniformly, then a step, or equivalently weight each step by 1/episode length. Record the style per episode. Train BC on single-style data by default, and use mixed-style data only with style or days_to_go conditioning, or with a model that sees history.

**Rationale.** Step-uniform sampling over-weights slow, long episodes, the opposite of what a speedrun needs. Mixed styles make the action distribution at a given state multimodal. A memoryless BC policy then switches strategies from day to day (for example, half-commits to two crop plans), which is catastrophic over long horizons.

### 15. [should] §6 Models (generalization to Remixed)

**Change.** Add an entity-centric head for macros parameterized by item. The logits for Buy(i, q), Plant(i, ·), Fish, Forage and Craft come from one shared MLP over [h_state, e_item(i), need[i], cover[i], held[i], price[i], q]. Macros without an item parameter use a standard linear head, and all logits are masked jointly. Keep the flat-head MLP as an ablation.

**Rationale.** A flat output layer learns each item macro independently and memorizes the Fixed request list. Sharing parameters across item features is what lets a policy act on request combinations it has not seen, which the Remixed and Remixed-OOD results require.

### 16. [should] §9 NeMo Gym (LLM track)

**Change.** Define LLM tasks as segments, not full runs. Sample start states from expert trajectories; the goal is to complete the next request or wing, or to play N=7 days. Each tool call takes either a day plan (a list of macros run until the day ends) or a single macro, with a cap on steps. Make the verify reward lexicographic: any success scores above any failure; among successes, faster is better, measured against the expert's days from the same state; partial credit applies only to failures and stays below the lowest success score.

**Rationale.** A full run is about 1.5–3k macro decisions. At up to 2k tokens per describe(), that is 3–6M prompt tokens per episode before any history, which is infeasible for GRPO's grouped rollouts. The current 'success + days + partial credit per slot', with no weights given, can rank a fast partial run above a slow success, the same misalignment as the RL reward. Segment tasks scored against the expert keep LLM results comparable with the RL tracks.

### 17. [should] §5 / §6 Data (storage)

**Change.** Define a Furrow dataset canonically as (content_hash, EnvConfig, seed, action sequence). Observation shards become a cache that can be regenerated with furrow replay --obs-layout <v> whenever the layout changes. Store shard arrays as separate uncompressed .npy files in a shard directory, which can be memory-mapped, instead of .npz. Human SDV data cannot be replayed and keeps full observations.

**Rationale.** The observation layout will change repeatedly during development, and several of these amendments add features. Replaying at ≥20k decisions/s rebuilds a 1,000-episode dataset in minutes. numpy cannot memory-map .npz members (np.load ignores mmap_mode for .npz), and deflate-compressed members cannot be mapped at all. That contradicts the 'memory-mapped shards' in §6, which matters with 29 GB of RAM.

### 18. [should] §7 SDV bridge, §8 stage 2 collect_human

**Change.** Specify that collect_human segments human primitive input into the SDV macro vocabulary using game events (warp, purchase, harvest, ship, bundle delivery). It writes expert_action = the inferred macro with a label_confidence, and macro=None for spans it cannot segment. State that Furrow and SDV share the API shape but not the meaning of observations or actions, so v1 claims no cross-environment transfer. Budget SDV finetuning explicitly as offline-to-online: a BC or IQL initialization, then a small number of online episodes.

**Rationale.** Human recordings are primitive inputs, so a macro policy has no labels without segmentation (VPT needed an inverse dynamics model for the same reason). At 1e2–1e3 ticks/s, a 100-day SDV episode (120k ticks) takes about 2–20 minutes of wall clock, which allows only on the order of 100 RL episodes per game instance per day. PPO-style finetuning at Furrow scale is not possible in the real game.

### 19. [could] §3.3 Primitive action space / §9 Furrow-Primitive-v1

**Change.** Mark primitive mode as a secondary track: about 1–2k decisions per day and about 1e5 per episode, which is beyond PPO's reach for this objective. Optionally record each macro's primitive expansion (prim_offset, prim_len) in macro datasets, which gives free primitive-level demonstrations with option boundaries for hierarchical work. In primitive mode, expose the item id on each shop-menu row in the observation.

**Rationale.** This keeps effort on the track that can succeed while still supporting hierarchical research. Currently the 'Menu option k' primitives point at rows whose contents cannot be observed; the observation has only an active-menu one-hot.
